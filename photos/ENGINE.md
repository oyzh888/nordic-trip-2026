# 相册引擎：分层、接口契约、不能破的规矩

网页（`public/photos/`）只是引擎的**一个**前端。命令行上传工具 `np_upload.py`、GPU 后处理端 `pipeline/`
是另外两个，以后可以再加（iOS 快捷指令、桌面同步工具、给别的行程用的另一套界面……）。
它们都只通过下面这套 HTTP 接口和引擎打交道，不碰数据库、不碰存储。

```
            ┌────────────── 前端（随便换、可以有很多个）──────────────┐
            │  网页 public/photos/   np_upload.py   iOS 快捷指令 …    │
            └───────────────┬───────────────────────────────────────┘
                            │  /photos/api/v1/*   /photos/f/{h}/{k}
┌───────────────────────────▼──────────────────────────────────────────────┐
│ 引擎（src/engine.js + src/album.js）                                       │
│   鉴权 · 上传 / 去重 / 断点续传 · 列表同步（全量 + 增量）· 搜索 · 人物 · 打包下载 │
│   字节 → R2（原件只写一次，永不改）   元数据 → Album（Durable Object, SQLite） │
└───────────────────────────▲──────────────────────────────────────────────┘
                            │  /photos/api/pipe/*（PIPE_TOKEN）—— 主动连进来，引擎不依赖它
            ┌───────────────┴────────────────┐
            │ 后处理 pipeline/worker.py（GPU） │  缩略图快车道 · 分析（描述/人脸/向量）· 聚类 · 转码
            └────────────────────────────────┘
```

`src/index.js` 只是**宿主**：挂网页静态文件，把 `/photos/api/*`、`/photos/f/*` 交给 `engine.handle()`。
换一套前端 = 换一个宿主（或者干脆是别处的静态网站 / App，用个人 API 密钥直接调接口）。

## 三条不能破的规矩

1. **存储优先。** 上传路径（probe → init → part → complete）只做两件事：字节进 R2、一行元数据进 Album。
   缩略图、EXIF、人脸、描述、转码全部是**事后补**的，补不上也不影响「照片已经安全存好、能浏览、能下载」。
   新功能要往上传路径里加任何计算之前，先问能不能挪到 `pipeline/` 里。
   Album 是单线程的：它在做重活（拼全量列表、聚类写几百行）的那一秒里，所有人的上传握手都在排队。
2. **改了列表里看得到的东西，就 `bump(h)`。** 前端靠增量同步跟上变化（见下），引擎靠 `bump(hs)` 知道是哪几张变了。
   说得清是哪几张就传 `bump(h)` / `bump([h…])`；只动了用户 / 人物 / 时刻 / 场景这几张小表传 `bump([])`；
   实在说不清才 `bump()`（所有前端会重拉一次全量）。`test/list_delta.py` 守这条：每个写请求之后比「增量拼出来的」和「全量」。
3. **原件只增不改。** 内容 ID = 文件字节的哈希，R2 里 `o/{h}` 写一次就不再动；派生出来的东西（`t/ p/ v/ f/ g/`）随时可以重做。

## 接口契约（给前端看的那部分）

完整用法和例子在 `public/photos/api.html`（线上 `/photos/api.html`）。这里只列契约本身。

**版本**：`/photos/api/v1/…` 和 `/photos/api/…` 现在是同一套。新前端请用 `v1`；以后要做不兼容的改动会开 `v2`，`v1` 保留。

**鉴权**（三选一）
| 谁 | 怎么带 | 能做什么 |
|---|---|---|
| 网页 | `np_sess` cookie（`POST /api/login` 发） | 全部用户接口 |
| 脚本 / 别的前端 | `Authorization: Bearer np_…`（网页「API 密钥」里生成，库里只存哈希） | 同上，等价于本人登录 |
| 后处理端 | `Authorization: Bearer <PIPE_TOKEN>` | 只有 `/api/pipe/*` 和写派生文件 |

**列表同步**
| 请求 | 回什么 | 什么时候用 |
|---|---|---|
| `GET /api/list` | 最新全量 `{ver, items, users, persons, scenes, moments, pipe, ai}`，带 ETag | 老前端 / 一次性脚本 |
| `GET /api/list?stale=1` | 全量，但可以是 10 分钟内拼好的那份（不让引擎为你再占一秒） | 前端第一次打开 |
| `GET /api/list?since=<ver>` | `{ver, delta: true, items: [变了的], gone: [h…], …全局小表（变了才带）}`；答不了时回全量（没有 `delta` 字段） | 之后每次轮询 |

合并增量：`gone` 里的拿掉；`items` 里已有的**原地替换**、没有的接在后面（这样同一秒拍的几张顺序和全量一致）；带了哪张小表就换哪张。
`ver` 相同 = 什么都没变。引擎重启后它的变更日志是空的，早于重启的 `since` 会拿到全量 —— 前端照常处理就对了。

**上传**：内容 ID（`h`）= SHA-256( 每 8 MB 一块各自 SHA-256、依次拼起来 )。
`probe`（按名字 + 大小先问一遍，命中就是秒传）→ `init`（回已经收到的块号）→ 缺哪块 `PUT part` 哪块 → `complete`。
≤ 8 MB 可以一步 `PUT /api/upload/file?name=`。5xx 和 503 `retry: true` 都可以退避重试；4xx 不要重试。

**文件**：`GET /photos/f/{h}/{k}`，`k` = `o` 原件 · `t` 缩略图（短边 360）· `p` 预览（长边 1600）·
`v` 720p 视频预览 · `g` 视频 H.264 新版 · `f` 人脸小图条。内容寻址、永久缓存；派生的还没做好时是 404，过会儿再来。
列表里每张的 `f`（flags）告诉你哪些已经有了：1 缩略图 · 2 预览 · 4 视频预览 · 8 人脸小图条 · 16 H.264 新版。

## 后处理端的契约（`/api/pipe/*`）

| 接口 | 用途 |
|---|---|
| `GET pending?aver=` | 待分析的（`aver` 低于当前分析版本）+ 排队的搜索词 + `upAgo`（几秒前有人在传）+ `conf`（人工确认过的人脸签名） |
| `GET nothumb?aver=` | 缩略图快车道：还没缩略图、还没分析的照片，新传的在前 |
| `POST results` | 一批分析结果（≤ 200 条，一次只刷新一次缓存）；`result` 是单条版 |
| `POST clusters` | 聚类结果（连拍 / 时刻 / 场景 / 人脸归属）—— 引擎只写有变化的行 |
| `GET embs?since=` / `faceemb?since=` / `faces?light=1` | 增量读向量 / 人脸（不要每次全量拉） |
| `PUT /api/upload/aux?k=t\|p\|v\|f` | 写派生文件，并在 flags 上打对应的位 |
| `WS ws` | 引擎推 `new`（有新照片）/ `recluster` / `q`（要算搜索词向量）/ `edit`；连着 = 网页上显示「AI 在线」 |

后处理端自己的规矩：有人在上传时（`upAgo < 30` 秒）不做聚类这类会长时间占着 Album 的重活；
逐张分析、补缩略图照做（它们对 Album 只是一两次很轻的写）。写回失败不要让进程退出 —— 跳过那一张，下一轮再试。

## 免费版的几个硬限制（换付费版前一直有效）

| 限制 | 影响 | 应对 |
|---|---|---|
| Worker 每个请求 10 ms CPU | 不能在 JS 里逐字节算哈希 / CRC | 整块读进来用原生 `crypto.subtle`；CRC 留给 GPU 端补 |
| Album 每天 10 万行写入 | 超了整个相册只读（2026-10-03 出过一次） | 只写有变化的行；变更日志放内存不落库；**不要在线上压测** |
| 请求体 100 MB | 大视频必须分块 | 8 MB 一块 |
